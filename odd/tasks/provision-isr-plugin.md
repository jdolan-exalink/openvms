# Provision-ISR camera plugin: LPR and native analytics (ODD)
Objective: ingest the analytics that Provision-ISR cameras compute themselves (LPR first, then whatever the real cameras prove to send), through the existing agent receiver, into OpenVMS central; configure and diagnose it from the camera configuration screen, detecting capabilities over ONVIF.
Branches (stacked-to-main, merged in this order, each PR targets the previous branch until the one below it merges): `feat/provision-isr-capture` (E0, base main) -> `feat/provision-isr-agent-registry` (E1 agent) -> `feat/provision-isr-plugin` (E1 central, UI and docs). Stage 0 and 1 only. Delivery: ask-on-risk. Runner: `go test ./internal/agent/... ./internal/api/... ./internal/onvif/...`, `go build` with and without cgo, `pnpm --dir apps/web test -- --run`. Full requirements: `odd/tasks/provision-isr-plugin.prompt.md` (verbatim copy of the user's prompt).

## Specs
- S1: "aprovechar primero el procesamiento de las cámaras y evitar duplicar inferencias en Frigate o OpenVMS cuando no sea necesario."
- S2: "No crear una integración paralela si podemos extender la existente." The existing code is `internal/agent/provisionlpr`, `apps/edge-agent/main.go`, `internal/api/provision_lpr_handlers.go`, `apps/web/src/components/provision/ProvisionLprSection.tsx`.
- S3: "No asumir que todas las cámaras soportan las mismas capacidades." / "Construir una matriz que diferencie funcionalidades confirmadas, pendientes de verificar y no soportadas." / "No inventes protocolos, endpoints ni capacidades del fabricante."
- S4: "Identificar inequívocamente la cámara de origen." / "Validar autenticación y origen." / "No confiar únicamente en la IP de origen como mecanismo de autenticación." / "Una cámara no autorizada no puede inyectar eventos."
- S5: "Implementar una cola persistente con reintentos e idempotencia." (stage 2, not in this branch)
- S6: "tenemos que configurar todo esto desde la parte de configuracion de camaras, estaria bueno detectar las capacidades de cada camara via onvif para que no sea tan manual y lograr una integracion simple" (user, L2).
- S7: "Agregar una sección **Analíticas de cámara** dentro de la configuración." showing manufacturer, model, firmware, plugin state, receiver address, last event, available analytics, source, connectivity diagnostics (prompt section 9).
- S8: "No desarrollar un componente rígido exclusivo de Provision-ISR." A provider interface comes in stage 3; stages 0 and 1 must not make it harder.
- S9: "Cambios de firmware desconocidos quedan registrados como payload no reconocido, sin descartar silenciosamente datos." (manufacturer document, section 16)

- L3 (2026-10-23): audit, all verified in code.
  - Exists: agent receiver on :7419 (`/SendKeepalive`, `/SendLPR`, `/LPR`, `/Notification/LPR`, `/v1/provision-lpr/{event,status,keepalive}`), heuristic parser (multipart/JSON/XML/form), 15 s dedup per camera and plate, in-memory heartbeat (last 20 events per camera), a configurator, a central status endpoint that polls the agent, the `ProvisionLprSection` UI, ONVIF probe data already stored per camera in `cameras.onvif_capabilities` (manufacturer, model, firmware, `has_analytics`, `has_events`, `supported_analytics` topics), a gRPC `EventService.PublishEvent` that only fans out to the realtime hub.
  - Gaps: no subscriber is wired to the receiver, so events never reach central and are lost on restart; central plates come only from Frigate (`lpr_reads`); in-memory queue of 256 drops when full; ingest routes and `/v1/provision-lpr/status` have no bearer check (`buildMux` in `apps/edge-agent/main.go`); the configurator posts to a guessed `/http/post.cgi` and returns success even when it fails; the parser drops anything without a plate; no common event model, provider interface or capability matrix.
  - Manufacturer document (`docs/Provision_ISR_LPR_Integracion_Plugin.docx`): the only real traffic captured is `POST /SendKeepalive` (empty body, expects 200). The LPR event format is NOT documented or captured and the document says not to code assumed field names; the routes `/SendLPR`, `/LPR`, `/Notification/LPR` and the CGI are not in it. The push is configured by hand in the camera web UI (Network > Advanced > HTTP POST, Protocol Type API, server address and port, heartbeat interval); there is also a documented Long Polling Port (8080) for external software. It covers LPR only: nothing about face, person or vehicle analytics.
  - Not audited yet: how Vision AI selects cameras and how alarm rules consume events (stage 3).
- L4 (2026-10-23): decisions and assumptions. (a) ONVIF defines no "HTTP POST server" setting, so over ONVIF OpenVMS can detect capabilities and subscribe to events, but cannot point the camera at the agent; to be confirmed on the real I6. (b) The camera's HTTP POST screen has no credentials field in the document, so authenticating the camera cannot rely on a secret in the request; E1.1 uses a registered-camera allow-list plus bearer on every control route, and the payload's own device identity once E0.4 shows whether one exists. (c) Existing deployments must keep working: enforcement starts when central pushes the first allow-list. (d) Stage 0 and 1 write no parser for the real LPR format; that waits for real captures.
- L5 (2026-10-24): E0.1 done. Bounded on-disk capture store (200 files / 64 MiB, IDs checked against a fixed pattern, credentials headers dropped, files 0600), receiver keeps unparsed requests by default and everything with `OPENVMS_AGENT_PROVISION_CAPTURE=all` (which also accepts POST on any path, logged as a warning), read routes behind the bearer in `buildMux`. A capture that cannot be stored never changes the 200 the camera gets. Doc: `docs/provision-isr/capture.md`. TDD note: tests were written with the code, no RED observed.
- L6 (2026-10-24): E0.2 and E0.3 done. `GetEventProperties` returned only element names that contained "motion" or "line" (it lost the hierarchy and never saw face or intrusion topics); it now returns full topic paths from the `wstop:topic="true"` leaves, sorted, deduplicated and capped at 200 (RED observed: old logic gave `[LineDetector MotionAlarm]`). `onvif.DetectAnalytics` maps topics to lpr, face, person, vehicle, line_crossing, intrusion, motion, tamper by whole words and always marks them `advertised`, with the topics as evidence; central stores it in `onvif_capabilities.analytics`; the camera screen shows it in `AdvertisedAnalytics` and says an advertised topic is not proof. - L7 (2026-10-24): stage 1 done, three defects found on the way. (3) The configurator posted the camera's credentials to a guessed `/http/post.cgi` and reported success; it now makes no call to the camera and success means a keepalive was seen (RED observed). Central: configure registers the camera, returns the values to enter, and verifies from the keepalives; new routes to unregister, read the registry and switch enforcement. UI: `ProvisionConfigureResult`, `ProvisionRegistryCard`, the credential fields are gone. Docs: `docs/provision-isr/setup.md`. Not verified here: nothing ran against a real I6 or a real agent host (E0.4 is still blocked on the camera); the central handlers beyond their pure helpers and the 401 checks have no handler-level test.

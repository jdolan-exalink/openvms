# Camera Web Proxy — robustez por servidor, self-signed y NVR

## Header
Task document: `odd/tasks/camera-web-proxy.md`.
Harden the `/camproxy` camera-web proxy so it works across every server and camera type,
accepts self-signed HTTPS, and can show an NVR's own web interface. Diagnosed from a live
representative sweep of all 5 servers (2026-10-31).

## Specs

- **S1** — "en la camara costanera no anda la web via proxy": the Costanera camera's web view via
  proxy must work. NOTE (diagnosis): from the API, Costanera http:80 already returns 200 and the
  page + sub-resources + GetLoadInfo all proxy successfully; the exact user-visible symptom must be
  confirmed before changing code (it may be the login flow, a non-default scheme/port, or a browser
  issue — do not fix blind). User has now confirmed a login-flow symptom on the Cochera camera: the
  configured username/password autofill works, but clicking the camera's login button appears not
  to submit or respond. Verify that the camera login request reaches the device through the proxy
  and that the result/redirect is handled in the embedded view. Before the latest rewrite, a live UI
  click sent `POST /DoLogin` through `/camproxy` and got HTTP 401, while Chrome reported a cross-frame
  `frames[0].document` TypeError. After rebuilding with the rewrite to `window.document`, a fresh
  proxy UI loaded `GetLoadInfo` with HTTP 200 and no browser errors, but Stream Type/Language stayed
  blank, Login had no visible label, and clicking produced no captured `DoLogin` request before the
  frame went blank. The remaining login flow is unresolved; the earlier 401 is not evidence about
  the current submission or the stored credentials. The required outcome is a live UI in which
  initialization completes, Login is actionable, the request is observed through the proxy, and the
  camera's result/redirect is handled. The user reports that the separate `camera-proxy.localhost`
  origin caused connection-refused behavior and explicitly requested returning to the previous
  setup with only the Login-button fix. Restore the app-relative `/camproxy` URL and opaque iframe
  sandbox; do not introduce a separate proxy hostname/listener or grant `allow-same-origin`. Preserve
  the configured camera credentials and make Login submit/navigate through the proxy. Verify the UI
  when an authorized app session is available; do not retry camera credentials after the previously
  observed HTTP 401. Successful camera authentication is not currently established.
- **S2** — "quiero que testees todas las camaras para asegurarnos que funciona de todos los servidores
  asi tenemos distintos tipos de camaras": test every camera across every server and camera type.
  Representative sweep results:
  - helv01 (agent OK, onvif endpoints): http:80 and http:8080 → 200 OK; https:443 → 502 `camera_unreachable`.
  - casa01: 409 `agent_unsupported` (agent too old for camweb).
  - fortunata: 409 `agent_unprovisioned` (no agent registered).
  - sodecar: 404 `camera_address_unknown` (cameras have no onvif_endpoint; stream-host fallback yields no private IPv4).
  - NVR-feedloot: 404 `camera_address_unknown`.
- **S3** — "si usan https autofirmado no tirar el error y aceptarlo y todo para que sea la mejor
  experiencia": a camera serving self-signed HTTPS must be accepted with no error. The agent already
  sets `InsecureSkipVerify: true` (internal/agent/camproxy/camproxy.go:175); verify the whole path
  (session probe + proxy) accepts a real self-signed https target and does not surface an error.
- **S4** — "en el caso de nvr tendriamos que poder ver la web de la nvr tambien": for an NVR server
  (kind=provision_nvr, NVR-feedloot at 192.168.68.200) the NVR device's own web interface must be
  viewable through the proxy, not only individual cameras (NVR cameras have no onvif_endpoint, so they
  currently 404 `camera_address_unknown`).
- **S5** — "cunado vas a servidores No se pudo verificar el estado del agente. No se ofrece instalar ni actualizar.":
  when agent status is unknown, unreachable, or the status API request fails, an authorized operator
  must be able to start the existing SSH discovery/recovery flow. This must not claim the agent is
  missing, start an install/update automatically, bypass SSH host-key trust, or skip explicit
  replacement confirmation.

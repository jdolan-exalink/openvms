# Face recognition (enterprise layer on Frigate)

## Objective
Make face recognition work end-to-end across federated Frigate servers, with a central per-tenant person registry, a dedicated Faces page, managed Frigate configuration, privacy controls like LPR, and known-person watchlist alarms.

## Problem and why
Today OpenVMS only detects whether a Frigate has `face_recognition.enabled` (badge in Servers). There is no way to enroll faces (no proxy to Frigate's `/faces` API), so libraries stay empty and nothing is recognized; recognized names only surface as raw `sub_labels` in events, with no per-person view, no score, no alarms (rules cannot match a person), and names are visible to anyone with `events.view`. Frigate's face recognition is off by default and needs a restart to enable. PRD audit (`docs/PRD_AUDIT.md`) lists face recognition as the first epic; the user prioritized it (2026-10-17).

## Frigate facts (sources: docs.frigate.video/configuration/face_recognition, docs.frigate.video/integrations/mqtt, github.com/blakeblackshear/frigate frigate/api/classification.py)
- Enabled under `face_recognition:` (global; per-camera `enabled`, `min_area`); keys `model_size` small|large, `detection_threshold`, `unknown_score`, `recognition_threshold`, `min_faces`, `save_attempts`, `blur_confidence_filter`, `device`. Restart required. Runs only on `person` detections, on the detect stream.
- A recognized name becomes the event `sub_label` (`["Name", score]`); MQTT `tracked_object_update` publishes every attempt (`type: face`, `name|null`, `score`).
- Library API: `GET /faces`, `POST /faces/{name}/create`, `POST /faces/{name}/register` (multipart), `POST /faces/{name}/delete` `{ids}`, `PUT /faces/{old}/rename`, `POST /faces/{name}/reclassify`, `POST /faces/reprocess`, `POST /faces/train/{name}/classify` (`training_file` or `event_id`), `POST /faces/recognize`. Admin auth on mutating routes. Per-version availability (0.17 vs 0.18) to be verified against the mock/real servers.

## Product decisions (user, 2026-10-17)
1. **Central registry**: OpenVMS stores persons and enrollment images per tenant and syncs them to every face-enabled Frigate in scope (drift detection, deletion propagation).
2. **Watchlists v1 = known persons only** ("person X seen", "anyone in list Y seen") via rules on ingested `sub_labels`; unknown-face alarms (MQTT ingestion) deferred.
3. **Strict privacy like LPR**: `faces.view` (see names/recognitions) and `faces.manage` (enroll/edit); face names redacted in events/alarms without `faces.view`; all access and changes audited; deleting a person removes central images, removes the face from every Frigate, and scrubs the name from stored event `sub_labels`.
4. **Managed config**: enable/tune face recognition per server and camera from OpenVMS (model size, thresholds) through the existing Frigate config editor, with restart-required notice.

### FACE-02 evidence (2026-10-17)
- Advisory fixes (commit `2374937`, migration 00056 edited in place, not deployed): image cap is race-safe (person row `FOR UPDATE`); rollback and blob deletion no longer use the request context (rollback uses a detached 15s context; blob keys go to the durable `face_blob_purge` queue in the same transaction that drops the image row, deleted by `Service.PurgeBlobs` in the worker with detached bounded contexts); `frigate_name` allocation relies on the unique index via `INSERT .. ON CONFLICT DO NOTHING` plus suffix retry; rename 404 is classified (FastAPI route miss `{"detail":"Not Found"}` -> unsupported; any other 404 stays `ErrNotFound`); rename comment corrected (route verified in 0.17 source, 0.18 not verified); redundant index dropped; seed comment fixed.
- Schema `migrations/00057_face_sync.sql`: `face_persons.sync_revision`; `face_server_sync` (job + per-server status per (server, person): pending/processing/synced/failed/conflict/disabled, `owned`, attempts, hard_failures, lease, backoff, last_error); `face_server_images` (central image -> Frigate image id per server). Both RLS-forced, server FK cascades (servers are hard-deleted).
- Sync design (`internal/faces/sync.go`, wired in `apps/worker/main.go` `runFaceSync`): registry writers bump `sync_revision` and re-queue non-disabled jobs; the worker enqueues missing jobs for live persons on every tenant server (new servers, new persons), flips disabled/pending by the server's `capabilities.face_recognition`, claims with `FOR UPDATE SKIP LOCKED` + 120s leases, and holds a per-person advisory lock (writers take it too) while reading desired state and writing to Frigate; the finish update is guarded by the claimed revision and `processing` state. Convergence is state based: list library, create face if absent, register missing central images one at a time (Frigate's new image id learned by diffing the library; mapping stored), delete unmapped ids in owned faces (drift and orphans from lost responses), delete the whole face for tombstones. Display-name edits do not bump the revision. Transient errors (unreachable, 5xx, 429) back off up to 15 min without limit; permanent ones count to 8 then `failed`; a remote "face recognition not enabled" answer parks the job as `disabled` for 10 min. Stored error text never contains paths, names or response bodies. Manual retry: `Service.RetrySync` (`faces.manage`, audited `FACE_SYNC_RETRIED`); status for the UI: `Service.ListSyncStatus` (`faces.view`).
- Ownership decision: NO name prefix. `frigate_name` stays the clean identifier so FACE-03 maps `sub_label` -> person directly. Ownership is tracked in `face_server_sync.owned`, committed before the create call (so a lost create response is still recognised): the sync only modifies or deletes faces it created or adopted while empty. A pre-existing same-named face with images is a `conflict` and is never touched (including on deletion of the central person); retry re-evaluates it.
- Tombstone purge: when no server holds an owned face with an unconverged state, the worker scrubs the person's `frigate_name` from `events.sub_labels` for that tenant (batched `array_remove`, exact match, idempotent, one `FACE_SUBLABEL_SCRUBBED` audit row per changed batch), then deletes the person row (`FACE_PERSON_PURGED`, actor `system:faces-sync`, ids and counts only). Blobs were queued at delete time.

### Open questions / known limits
- Capability refresh is still manual (`SyncServer`); a Frigate that enables face recognition is only noticed after a server re-sync (remote "disabled" answers back off 10 min).
- A tombstone whose owned face sits on a server that stays disabled/unreachable is never purged (name stays in events). No operator override yet.
- Re-ingestion of a still-recent review from Frigate after the purge can write the name back into `events.sub_labels`; a hashed deny-list would close it (candidate for FACE-03/05).
- Deleting an empty owned face folder relies on a bogus-id delete probe (Frigate removes empty folders after a delete); unverified against a live server. Frigate-side images added by hand to an owned face are removed as drift; FACE-03 train-from-detection must add images centrally first.
- sub_labels namespace is shared with Frigate LPR known-plate labels; scrub is exact match on `frigate_name`.

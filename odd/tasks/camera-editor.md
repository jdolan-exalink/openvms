Facts found by the explorer (L2) that shape the work:
- The editor is the full page `/cameras/$cameraId/frigate` (`FrigateCameraConfig.tsx`), not a popup; it opens on the first Frigate schema section (`enabled`), not on General (`activeSection = active ?? sections[0] ?? GENERAL`, line ~201).
- `CameraGeneralForm` saves OpenVMS-only data (name, enabled, quality, location, tags); `CameraOnvifPanel` and the ONVIF facts in `CameraIdentity` hold the informational ONVIF data.
- Most requested fields are Frigate sections (`enabled`, `ffmpeg.inputs`, `audio`, `lpr`, `face_recognition`, `timestamp_style`, `audio_transcription`, `best_image_timeout`); `Camera.lpr` and `Camera.face_recognition` in OpenVMS are read-only mirrors of Frigate; there is no real "camera type" field, only tags.
- Provision LPR: the Configurator cannot change the camera (manual instructions only); success is declared when a keepalive arrives from the registered IP; there is no "test" button; routes `provision-lpr/*` are not in the OpenAPI.
- There is no camera called "Helv01": helv01 is a server. Its Provision cameras are Cementerio (I6-340IPEN-MVF-V5), Escuela (I6-240LPRN-MVF2, tags lpr+provision) and Ingreso Sur (I6-320LPR-MVF2).

Assumptions (not asked by the user; confirm or drop):
- A4. The web view is a reverse proxy under the OpenVMS origin (`/api/v1/cameras/{id}/web/`), authenticated like the rest of the API, never an open relay: the camera address is resolved server-side from the camera record and the browser can only reach that one host and port. It rewrites root-relative URLs, redirects and cookie paths, and removes frame-blocking headers. Works for plain request/response web UIs; WebSocket or heavy script UIs are best effort and are the first thing to verify on the real camera.
- A5. The manufacturer documents no remote way to set the HTTP POST screen (docs/provision-isr/capability-matrix.md), and an earlier guessed CGI was removed because it reported false success. So remote configuration is learned from a real capture and replayed; until a template exists for a model the guided manual flow and the web view remain the way.
- A1. The top "camera enabled" switch writes both OpenVMS `cameras.enabled` and Frigate `enabled`, so disabling a camera also stops Frigate from processing it.
- A2. "Camera type" is a real choice in General with three values, stored as tags (no new database column): `generic`, `lpr_frigate` (Frigate's own LPR engine reads the plates: Cementerio) and `lpr_provision` (the camera's integrated Provision analytics send the plates to our agent: Escuela and Ingreso Sur). Changing it only touches the tags and, for `lpr_frigate`, the camera's Frigate `lpr.enabled`.
- A3. The LPR "test" observes: it registers the camera, waits for a keepalive from its IP and reports pass/fail with last seen and counters; it cannot push configuration into the camera.

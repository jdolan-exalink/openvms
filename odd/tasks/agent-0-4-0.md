# Edge agent 0.4.0: REST-only transport, remote servers, console tokens, curl install (ODD)
Objective: an edge agent that OpenVMS can reach over a published HTTPS/REST address (LAN, VPN or a Zero Trust tunnel), that installs from GitHub with one curl command, that is managed with its own tokens from the console, and that never has to open a connection to OpenVMS. Branch: `feat/agent-0-4-0` (plan on it; each stage gets its own branch off `main`). Delivery: stacked-to-main, one PR per stage (assumption, as in the previous features; confirm before A0). Runner: `go test ./apps/edge-agent/... ./internal/agent/... ./internal/provision/... ./internal/api/...`, `go test -tags integration` for the packages that touch Postgres, `go build` with and without cgo, `pnpm --dir apps/web test`.

## Specs
- S1: "tenemos que soportar conexion API REST para toda la info que traemos y llevamos, actualizaciones de agentes etc"
- S2: "ya que aveces tenemos servidores que no estan en la misma lan y la idea podria ser o publicar via zerootrust el puerto api rest del agente o via vpn"
- S3: "tenemos que poder via consola crear un apitoken"
- S4: "tenemos que poder installar via comando curl los agentes en los servidores como tambien desde el host que tiene el agente conectarlo a un server openvms"
- S5: "tengamos en cuenta que los escenarios, openvms con acceso via apirest a frigate y agente osea a 2 direcciones distintas, o conexion directa via LAN o VPN"
- S6: "yo creo que con openvms llegando ya tenemos que estar y que el agente se instale via curl de github y oopevms hace consultas via api rest del agente" (user, L3). Decision: OpenVMS always initiates; the agent never connects to OpenVMS.
- Assumptions (not asked): publishing the agent address (tunnel, VPN, port forward) is the operator's job and outside OpenVMS; agents 0.3 keep working unchanged next to 0.4 ones; the repository is public, so GitHub Releases can serve the installer.

## Tasks
Findings the plan rests on are in L2. A0a comes first because it is a live failure (L4).
- [ ] A0a — S2,S6: install behind NAT. When OpenVMS can reach the host but the host cannot reach OpenVMS, the SSH install must finish: an install option ("the server cannot reach OpenVMS") that skips the mTLS enrollment and its 30 s wait (`waitForFreshAgentEnrollment`), registers the agent by token over the HTTPS/HTTP health check OpenVMS already does, and says in the result that the agent will be polled. Without enrollment there is no gRPC heartbeat, so the agent status needs the central poll of A2 (a minimal version ships with this task). Also: a failed registration must not leave an installed but unregistered agent without telling the operator. Risk: item 2 (auth path) and item 3.
- [ ] A0 — S1,S5: foundations. One source for the agent version (`internal/agent.Version` reads `buildinfo`; `deploy/agent/VERSION` becomes 0.4.0; CHANGELOG, VERSIONING). An `AgentEndpoint` type (scheme, DNS name or IP, port) replacing the ~10 `net.ParseIP(host).To4()` checks and the fixed `http://`/`https://` in `internal/provision`; additive migration `server_agents.base_url` (nullable, falls back to host:port). Frigate and agent addresses stay independent fields. Risk: item 3 (config format others consume) and item 1 (additive migration).
- [ ] A1 — S2,S5: remote transport. Verify the agent by host name with system roots (no separate secure port, 443 behind a tunnel); optional extra request headers per agent, stored sealed (the service token a Zero Trust gateway needs); guard against central being used as an SSRF proxy now that a DNS name or URL is accepted (deny loopback, link-local and metadata addresses unless explicitly local, resolve and check at dial time). Risk: item 2.
- [ ] A2 — S1,S6: REST status replaces the gRPC heartbeat for 0.4 agents. Agent serves `GET /v1/status` (identity, version, uptime, metrics, network); a worker job polls it and feeds the same agent status central reads today; gRPC heartbeat stays for agents up to 0.3. Mixed fleets keep working. Risk: item 3.
- [ ] A3 — S3,S4: tokens from the console on the agent host: `openvms-agent token create|list|revoke|rotate` over a hashed store (name, scope read/control/update/events, expiry, last used); the legacy single token file stays valid as full scope. `vmsctl token` gains scopes for OpenVMS API tokens if the audit shows they are missing. `openvms-agent connection` prints what to enter in OpenVMS (URL hint, token). Risk: item 2.
- [ ] A4 — S1: update over REST with rollback. `POST /v1/update` verifies sha256 and identity, keeps the previous binary, restarts, health-checks itself and rolls back on failure; central uses it for URL-based agents (the SSH path stays). Risk: item 5 and item 4.
- [ ] A5 — S4,S6: install from GitHub. A release workflow on tag `agent-vX.Y.Z` builds linux/amd64 and linux/arm64, writes sha256 files and publishes the binaries and `install-agent.sh` as release assets; `curl -fsSL <release>/install-agent.sh | sudo bash` installs binary, systemd unit and env, creates the first token and prints the connection data; flags for port, TLS, version, upgrade, uninstall; verifies the checksum. Risk: item 5.
- [ ] A6 — S4,S5,S6: connect it in OpenVMS. `PUT /api/v1/servers/{id}/agent/connection` (URL, token, optional headers) that verifies against `GET /v1/status` before saving; a section in the server configuration screen with a test button; `vmsctl agent-connect` for the console. Replaces `agent-register` for remote hosts. Risk: item 2.
- [ ] A7 — S2,S5: topologies runbook (LAN direct, VPN, Zero Trust; Frigate on its own URL), compatibility matrix for 0.3 agents, release notes. inline

- L2 (2026-10-24): audit (read-only explorer). Shipped agent version is `deploy/agent/VERSION` (0.3.0) injected as `buildinfo.Version`; `internal/agent/version.go` is a separate stale "0.2.1" still used for the heartbeat and the `server_agents.version` column. Central dials the agent over plain HTTP on :7419 (metrics, update, ONVIF, LPR, events); the agent dials central only over gRPC (heartbeat, certificate renewal) plus the REST enroll call. IPv4-only checks live in `agent_onvif_probe.go`, `agent_tls.go`, `agent_tls_config.go`, `agent_update_service.go`, `agent_uninstall_service.go`, `onvif_discovery.go`, `agent_install*.go`, `ssh.go`, `vmsctl agent-register`; schemes are fixed and the certificate check is against the registered IPv4. `PlainAgentHTTPClient.Do` refuses query strings. User API tokens exist (`api_tokens`, `vmsctl token -user -ttl`, Bearer auth in `internal/api/auth.go`). The agent token lives in `/etc/openvms/agent.token`, sealed in `server_agents.token_sealed`. `POST /v1/update` replaces the binary with no rollback; the SSH update has rollback. There is no curl installer (`deploy/agent/install.sh` installs the Frigate compose bundle); the SSH install is the only way. `frigate_servers.base_url` and `server_agents` are independent. No release workflow exists in `.github/workflows` (only `ci.yml`); the repository is public.
- L3 (2026-10-24): answer to the question "can remote servers reach OpenVMS or only OpenVMS reach them": "yo creo que con openvms llegando ya tenemos que estar y que el agente se instale via curl de github y oopevms hace consultas via api rest del agente". Consequences: no agent-to-OpenVMS heartbeat, enrollment or "connect --server"; the heartbeat becomes a central poll (A2); the installer comes from GitHub Releases, not from OpenVMS (A5); "connect" means registering the published agent URL and token in OpenVMS (A6).
- L4 (2026-10-24): live failure, quoted: "el tema que tengo hoy por ejemplo es que tengo acceso full al servidor frigate con agente pero el servidor no me ve a mi porque estoy detras de un nat y en este momento no se instala el agente que tira una falla al final" followed by the job log ending "[STAGE] Registrando credenciales y verificando certificados TLS… [ERROR] La operación falló o se interrumpió." and "esto no tendria que suceder, si los equipos estan en la misma red funcionan correctamente". Reproduced from the API log of task `54e14d67-2095-49a4-be68-1674d0c35012`: `agent install registration failed … reason=enrollment_verification`, 30 s after the service was activated. Cause (code): with the agent listener configured, `runAgentInstall` in `internal/provision/agent_install_service.go` (~line 380) calls `waitForFreshAgentEnrollment`, which polls for up to 30 s for a certificate that the agent obtains by calling OpenVMS (enroll over HTTPS, then gRPC); a host behind a NAT that cannot reach OpenVMS never does, so the job fails before the HTTPS health check and the registration, which OpenVMS-to-agent would have passed. This is the agent-to-OpenVMS dependency that S6 removes.
